# Eventos SIFEN

This document summarizes SIFEN events from MT 150 and the relevant Notas Tecnicas (NTs). It is a domain/reference document, not an SDK implementation document.

## Event Concept

MT 150 defines an event as an occurrence registered in SIFEN by which a mark is assigned, or the state of a Documento Electronico (DE) or Documento Tributario Electronico (DTE) is modified or affected during its lifecycle. Events can occur before or after DTE approval depending on their nature (MT 150 p. 112).

Events are split by registration mode:

- Automatic registration: generated by SIFEN. Example: adjustment event generated when a Nota de Credito Electronica or Nota de Debito Electronica associated to a Factura Electronica is approved (MT 150 p. 112, p. 113, p. 115).
- Required registration: submitted through SIFEN Web Services or the SIFEN portal by an actor such as the issuer or receiver (MT 150 p. 112, p. 118).

Events are also classified by actor:

- Emisor events: originated by the issuer when a situation modifies numbering, content, or state of a DE/DTE (MT 150 p. 112-114).
- Receptor events: originated by the receiver of a DE/DTE, such as conformity, disconformity, desconocimiento, or notification of receipt (MT 150 p. 114-115).
- Automatic SIFEN events: generated without direct issuer or receiver intervention and returned as part of DTE consultation/event containers (MT 150 p. 115).
- SET-origin events: described as future in MT 150. Impugnacion de DTE is named, but detailed current fields are not provided in the base MT (MT 150 p. 116).

## Where Events Appear

### DE Consultation

`siConsDE` queries a DE by CDC. On success, SIFEN returns `xContenDE`, a DE consultation container (MT 150 p. 50-51).

The consultation container contains:

| Field      | Meaning                                            | Occurrence | Source       |
| ---------- | -------------------------------------------------- | ---------- | ------------ |
| `rDE`      | XML of the DE                                      | 1-1        | MT 150 p. 51 |
| `dProtAut` | Transaction/protocol number associated with the DE | 1-1        | MT 150 p. 51 |
| `xContEv`  | Event container entries associated with the DE     | 0-n        | MT 150 p. 51 |

MT 150 describes `xContEv` as information for all events registered by SET, or available from the issuer, up to the current date (MT 150 p. 51).

Each event container has:

| Field              | Meaning                                             | Occurrence | Source       |
| ------------------ | --------------------------------------------------- | ---------- | ------------ |
| `xEvento`          | Event XML payload                                   | 1-1        | MT 150 p. 52 |
| `rResEnviEventoDe` | Optional response from event reception/registration | 0-1        | MT 150 p. 52 |

### Event Registration

`siRecepEvento` registers events in SIFEN. It is synchronous (MT 150 p. 52-53).

| `dEvReg`        | Event payload XML                    | 1-1        | MT 150 p. 52 |

Response shape:

| Field              | Meaning                                                     | Occurrence | Source       |
| ------------------ | ----------------------------------------------------------- | ---------- | ------------ |
| `rRetEnviEventoDe` | Response root                                               | 1-1        | MT 150 p. 53 |
| `dFecProc`         | Processing date/time                                        | 1-1        | MT 150 p. 53 |
| `gResProcEVe`      | Processing result for each event                            | 1-15       | MT 150 p. 53 |

The success code for event registration is `0600` (MT 150 p. 158).

## Event XML Anatomy

Events are structured under `gGroupGesEve` (MT 150 p. 120):

```xml
<gGroupGesEve>
  <rGesEve>
    <rEve Id="...">
      <dFecFirma>...</dFecFirma>
      <dVerFor>150</dVerFor>
      <gGroupTiEvt>
        <!-- exactly one event-type-specific element -->
      </gGroupTiEvt>
    </rEve>
    <Signature>...</Signature>
  </rGesEve>
</gGroupGesEve>
```

Common fields:

| Field         | Meaning                                                        | Source        |
| ------------- | -------------------------------------------------------------- | ------------- |
| `rGesEve`     | Event management root. Up to 15 events per batch.              | MT 150 p. 120 |
| `rEve`        | General event fields.                                          | MT 150 p. 120 |
| `rEve@Id`     | Event identifier. This is not the CDC.                         | MT 150 p. 120 |
| `dFecFirma`   | Event signing date/time.                                       | MT 150 p. 120 |
| `dVerFor`     | Event format version.                                          | MT 150 p. 120 |
| `gGroupTiEvt` | Event type group. The child element identifies the event type. | MT 150 p. 120 |
| `Signature`   | Digital signature of `rEve`.                                   | MT 150 p. 120 |

Important distinction: `rEve@Id` is the event identifier. Most event payloads also contain a field named `Id`; in documented event payloads except inutilizacion, this payload `Id` is the CDC of the affected DE/DTE. Inutilizacion does not have a CDC because it applies to a timbrado/number range.

MT 150 requires each event to be digitally signed, and event batches can contain up to 15 events of any type (MT 150 p. 118). The signature is part of the legal XML artifact, but SIFEN is responsible for validating it when the event is registered.

## Receptor Event Semantics After NT 019

NT 019 is the most important receptor-event update.

The old receiver-event transition table from MT 150 p. 119 is removed. The current rule is:

> Any receiver event is valid as long as it is within the established deadline. The last registered event is valid and unalterable.

Deadline counting after NT 019:

| Document state | Deadline reference |
| -------------- | ------------------ |
| DE             | Emission date      |
| DTE            | Approval date      |

NT 019 also adds or modifies rules so receiver events cannot be registered on cancelled DTEs, adds maximum-event validations, and separates DE emission-date deadlines from DTE approval-date deadlines.

NT 019 adds signature validation code `0143`: the digital signature of a receiver event must correspond to the receiver of the DE/DTE.

## Validation Overview

MT 150 p. 150 groups event validation codes:

| Range                      | Event area                           |
| -------------------------- | ------------------------------------ |
| 4000-4049                  | Cancelacion                          |
| 4050-4099                  | Inutilizacion                        |
| 4100-4113 and NT additions | Notificacion - Recepcion             |
| 4150-4158                  | Conformidad                          |
| 4200-4207                  | Disconformidad                       |
| 4250-4265                  | Desconocimiento                      |
| 4300-4336                  | Actualizacion de datos de transporte |
| 4451-4478                  | Nominacion FE, added by NT 014       |

Important validation notes:

- `0600` means event registered successfully in `siRecepEvento` (MT 150 p. 158).
- `0560` means the `siRecepEvento` input message exceeds 1000 KB (MT 150 p. 158).
- Cancellation validation `4004`, which blocked cancellation after receiver confirmation, is removed by NT 025.
- Transport event validation codes `GET022` through `GET030` are corrected by NT 018, and NT 018 adds `GET002` code `4336` for CDC nonexistence.
- Nominacion FE validation comes from NT 014, plus the NT 027 ID-type correction.

## Signature and Certificate Notes

All events must be digitally signed (MT 150 p. 118). The `Signature` group signs `rEve` (MT 150 p. 120).

NT 016 updates the general signature/certificate rules. Relevant changes include:

- Supported signature methods include RSA-SHA-256, RSA-SHA-384, and RSA-SHA-512.
- Supported digest methods include SHA-256, SHA-384, and SHA-512.
- Enveloped Signature is the valid transform.
- XPath under Transform is removed.
- Several certificate-chain and revocation-related checks move into format/certificate validation rules.

For receiver events, NT 019 adds the specific validation that the event signature must correspond to the DE/DTE receiver.

## Open or Future Areas

MT 150 names SET-origin events such as Impugnacion de DTE as future (MT 150 p. 116). The base MT does not provide enough current field detail to treat those as fully specified.

Endoso de FE is also presented as a future event in MT 150 p. 114. If later NTs or observed SIFEN XML define it fully, it should be added to the event catalog.

Because SIFEN can update event behavior through NTs, always check the latest NT index before treating this document as exhaustive.
